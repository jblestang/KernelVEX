## 1. Cybersécurité, CRA & Conformité OpenVEX 0.2.0

### Points conformes
- **Principe fail-closed strict (`openvex.py`) :** Tout check inconnu ou tout résultat marqué `unexpected failure` (par exemple échec `kmax`, fichier Kbuild illisible ou erreur interne `cve-triage`) force systématiquement le statut `under_investigation` sans jamais émettre `not_affected` silencieusement. Seule la liste blanche `NOT_AFFECTED_CHECKS` (checks de `convert_openvex.py` + `check_kconfig_quick` en mode conservateur) peut produire `not_affected` avec justification `vulnerable_code_not_present` et `status_notes` traçables.
- **Provenance cryptographique complète (CRA) :** Le bloc `meta` impose par schéma JSON Draft 2020-12 le SHA-256 brut de la configuration noyau (`kernel_config_sha256`, 64 hex), le commit SHA-1 complet de `cip-kernel-sec` (`sec_commit`, 40 hex), les versions/commits épinglés (`tooling_pins`), ainsi que `kernel_source_commit` (40 hex en mode `full`, `null` en mode `quick`).
- **Conformité OpenVEX v0.2.0 et mode strict :** Par défaut, le document produit est validé contre [`openvex_v0.2.0_meta.schema.json`](file:///Users/jean-baptiste/KernelVEX/schemas/openvex_v0.2.0_meta.schema.json). L'option `--strict-openvex` émet un document strictement conforme au schéma officiel OpenVEX sans propriété racine supplémentaire (validé contre [`openvex_v0.2.0.upstream.schema.json`](file:///Users/jean-baptiste/KernelVEX/schemas/openvex_v0.2.0.upstream.schema.json)) et écrit la provenance dans un fichier compagnon `.meta.json`. Les copies embarquées dans le paquet Python sont vérifiées octet pour octet par test automatisé.
- **Identifiants `@id` IRI & PURL noyau :** Les versions comportant `+` (par exemple `localversion` du type `+dirty`) sont encodées via `urllib.parse.quote(..., safe=".-_")` dans l'IRI `@id`. L'option `--product-purl` permet une correspondance exacte 1:1 avec un SBOM CycloneDX ou SPDX existant sans heuristique ambiguë.
- **Zéro catalogue artisanal ni CVE inventée :** `tests/test_no_fictional_cves.py` audite l'ensemble du dépôt (sources, tests, CI, docs, schémas) afin d'interdire tout préfixe fictif de test, identifiant CVE artificiel ou catalogue Kconfig JSON maintenu à la main. L'unique source CVE provient de `cip-kernel-sec` et des enrichissements générés par `cve-triage enrich`.

### Constats identifiés et corrigés
1. **Dérivation PURL `kernel.org` vs `url2purl` (`openvex.py`) — CORRIGÉ :** `packageurl-python` (`url2purl.get_purl`) sur les dépôts `git.kernel.org` produisait un PURL `pkg:generic/linux.git?download_url=...` peu exploitable par les outils SBOM. Ajout d'une normalisation explicite pour les hôtes `kernel.org` / `*.kernel.org` vers `pkg:generic/kernel.org/linux@<version>?arch=<arch>&config=<config>`, complétée par le fallback générique pour les sources locales non-URL.
2. **Sélection CVE vide silencieuse (`catalog.py` + `full.py`) — CORRIGÉ :** Un filtre CI mal configuré (année future ou branche incompatible) sélectionnant 0 CVE doit échouer en mode fail-closed (`KernelVexError`, code retour `20`) plutôt que de produire un OpenVEX vide avec code `0`. Les branches inatteignables ajoutées initialement dans `full.py` ont été retirées afin de préserver ce contrat strict et d'éviter tout passage d'une liste vide à `cve-triage` (`nargs="+"`).

## 2. Noyau Linux, Kconfig/Kbuild & CIP SLTS

### Points conformes
- **Réutilisation intégrale du moteur OSS :** Aucune réimplémentation de `kmax`, ni de parseur Kbuild, ni de résolution d'ancestralité git. En mode `full`, `kernelvex` prépare le contexte et délègue intégralement l'analyse au binaire épinglé `cve-triage` (`triage` et `enrich`).
- **Support double profil sans duplication (`profile.py`) :** Auto-détection `*-cip*` (y compris `-cipN` / `-cip-rt`) ou forçage `--profile {cip,standard}`. Le flag `--cip` n'est transmis à `cve-triage` que pour le profil `cip`; en profil `standard`, les CVE purement CIP sont filtrées.
- **Support `.config` brut et `/proc/config.gz` (`kconfig.py`, `full.py`) :** Décompression en mémoire avec calcul SHA-256 des octets bruts d'origine, inférence automatique de `detected_arch` / `ARCH` Kbuild, et écriture d'un `input.config` temporaire hors du dépôt noyau afin de ne jamais souiller le checkout source.
- **Pré-vérifications git robustes (`full.py`) :** Résolution prioritaire de la révision via `^{commit}` (résout directement le commit sous-jacent des tags annotés) et vérification préalable de `git describe --abbrev=0 <rev>` exigé en interne par `cve-triage` (évitant des échecs cryptiques sur clones shallow sans tags).
- **Isolation et préservation du dépôt source (`full.py`) :** Création d'un `git worktree add --detach` éphémère avant `make alldefconfig` (avec nettoyage systématique dans un bloc `finally`), et repli automatique sur `git clone --shared --no-checkout` lorsque le dépôt source est monté en lecture seule en CI (`-v ...:/sources:ro`).
- **Cache `.kmax` persistant (`full.py`) :** Clé déterministe `<cache_dir>/kmax/<profile>-<commit[:12]>-<arch>.kmax`, vérifiant explicitement que la cible n'est pas un répertoire (requis par la sérialisation pickle de `cve-triage`).

### Constats identifiés et corrigés
1. **Fixtures git de test pour `git describe` (`tests/test_full_wrapper.py`) — CORRIGÉ :** `cve-triage` appelant `git describe --abbrev=0` sans `--tags`, la fixture de dépôt git utilisait initialement un tag léger au lieu d'un tag annoté (`git tag -a`). Corrigé pour refléter le comportement réel des arbres `linux-cip` et `linux-stable`.
2. **Expectation fixture CIP en mode `quick` (`tests/test_catalog_and_quick.py`) — CORRIGÉ :** Vérification sur le YAML réel `CVE-2024-40901.yml` confirmant que `v5.10.224-cip52` est postérieur à `fixed-version` (`v5.10.221-cip50` → `check_fixed_by`), tandis que `v5.10.220-cip49` démontre l'exclusion Kconfig `check_kconfig_quick` (`CONFIG_SCSI_MPT3SAS` absent).

## 4. Conteneurisation OCI Non-Root & Intégration CI/CD

### Points conformes
- **Conteneur non-root & versions épinglées (`Dockerfile`, `PINS.lock`) :** Image `ubuntu:24.04` exécutée sous UID/GID `10001` (`kernelvex`), virtualenv isolé `/opt/venv` respectant la contrainte `setuptools<82` pour `kmax==4.10` et `kernel-cve-triage` épinglé au SHA complet `3aa04484d7b0e58331d3da4b2aef78376f23de55`, volume `/cache` persistant et `ENTRYPOINT ["kernelvex"]`.
- **Contrat de codes retour CI déterministe (`0`, `10`, `20`, `30`) :** Distinction stricte entre triage propre (`0`), éléments ouverts `under_investigation`/`affected` non bloquants (`10`), erreur outillage/entrée/schéma (`20`) et dépassement de politique `--fail-on` (`30`). Exemples fournis pour GitLab CI et GitHub Actions.

### Constats identifiés et corrigés lors de la revue
1. **Binaire `clang` absent dans `Dockerfile` — CORRIGÉ :** `libclang-dev` et `clang-tools` étaient installés mais pas le paquet `clang` lui-même, nécessaire si un arbre noyau / workflow `kmax` invoque `CC=clang` ou `HOSTCC=clang`. Paquet `clang` ajouté au bloc `apt-get install`.
2. **Ownership `git` sur volumes montés en lecture seule en mode non-root (`Dockerfile`) — CORRIGÉ :** L'exécution sous `USER 10001:10001` face à un montage `-v ...:/sources:ro` appartenant à l'UID runner hôte (`1000`/`1001`/`0`) déclenche l'erreur git `dubious ownership` (`detected dubious ownership in repository`). Ajout de `git config --system --add safe.directory '*'` au build de l'image.
3. **Droits d'écriture des bind mounts Linux pour UID `10001` (`scripts/verify_full_linux.sh`) — CORRIGÉ :** Ajout de `chmod 0777 "${CACHE_HOST}" "${OUT_HOST}"` dans le script d'intégration Linux avant lancement des conteneurs afin de garantir l'écriture dans `/cache` et `/out` par l'utilisateur non-root `10001`, plus vérification explicite de `clang --version` à l'étape `[2/6]`.
